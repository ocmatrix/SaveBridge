## 0. 一页纸总览

**方案（决定 1，已定）：** 每条链提议**一个批量提案**，里面按顺序放两个动作：①升级桥合约到带手续费的新实现；②写入手续费配置（收款地址、费率/档位）。只等**一个倒计时**（最短 48 小时，由提议时的 `delay` 决定，建议不超过 7 天）。批量提案**原子执行**：两个动作要么都成功，要么都不生效。**到期后由 ss02 付款程序里的自动执行服务执行（见核心事实 2），所以倒计时结束的那一刻就是手续费生效的那一刻。**

| 阶段 | 做什么 | 链上写入 | 授权 | 需要等 |
|---|---|---|---|---|
| P0 | 冻结代码、全部测试、BSC 分叉演练、配套代码就位 | 无 | 否 | — |
| P1 | 两条链各部署一个**新实现合约**（不动线上代理） | 有（部署者各 1 笔） | **G1** | — |
| P2 | 管理钱包在两条链**提议批量提案**（进时间锁排队；**`delay` = 计划生效时间 − 现在，至少 48 小时**） | 有 | **G2**（同意手续费在这个时刻自动生效） | `delay` |
| P3 | **等待窗口内**：发布新版用户页与管理页、监控改造上线、App 新版上架并覆盖用户；**放行条件不满足就取消提案** | 无链上写入（取消除外） | **G3** | 至 App 覆盖达标 |

| P5 | 现场核对 + 真实小额交易验证 | 小额交易 2 笔 | **G4**（验证交易） | — |

**核心安全事实（已核实）：**
1. 升级只有时间锁能做；**排队的 48 小时里线上仍是旧合约，所有功能照常**。
2. **提案到期后会被自动执行，不是我们手动按。** ss02 的付款程序里有「提交服务」（`packages/relayer/src/timelockExecutor.ts`），每 60 秒检查两条链，把**已到期、未被取消、同一管理员纪元、未过期**的时间锁提案自动 `executeBatch`（用的是没有任何合约权限的提交热钥匙；设计文档 §4.1 也是这样规定的），到期前 24 小时和 6 小时还会通过 Telegram 提醒负责人（这一点我读了代码，没有在现场确认提醒是否已送达）。**所以「最早可执行时间」就是「手续费生效时间」。** 控制它的办法是提议时的 `delay`（至少 48 小时；我只验证过 6 天可行，建议不超过时间锁的 `MAX_DELAY` = 7 天，更长没试过），日期有变就取消并换盐重新提议。有效期是到期后 14 天。我已在 ss02 上确认该服务所在的版本里有这段代码、付款程序在运行。
3. **手续费在批量提案执行的那一刻立刻生效**，没有缓冲。因此**§7 的放行条件必须在到期时刻之前全部满足**；到期时刻之前任何一条没满足，就取消提案（管理钱包或白名单钱包都能取消），不要指望到点再手动拦。
4. 执行后：不带 `value` 的老调用方式会**直接失败**（合约要求带手续费）。所以**老版用户页、老版 App 在执行后都不能再转账**，用户必须已经在用新版。
5. 为了让新版用户页能**在升级之前就发布**（等待窗口内），用户页已加兼容：**调用 `quoteNativeFee` 被回滚（说明旧合约）时按「无手续费」处理**，网络错误则照常报错，不会误当成没有手续费。App 也必须做同样的兼容（见 `NATIVE-FEE-APP-FLUTTER.md` §7）。
6. 时间锁执行后会自检（`_checkBridgeSane`）；批量里任何一步失败（含配置步骤因桥处于暂停而被拒），**整个批量回滚，线上状态不变**。**桥处于暂停时执行会整批回滚**：升级允许暂停时进行，但写手续费配置要求未暂停。注意自动执行服务每分钟重试，**解除暂停后一分钟内批量就会自动生效**；因此到期后处于暂停状态、而放行条件还没满足时，要先取消提案，不要只靠暂停拖着。
7. 手续费新增的存储放在两个新的独立命名空间，**不改动原有存储**，回滚到旧实现不会破坏数据。
8. 管理钱包可以**立即关闭手续费**（`disableNativeFee()`，不用等时间锁）。

### P0-4 本地分叉演练（BSC），要演练**批量提案**本身
目的：在真实线上状态上预演「批量执行 → 升级成功且配置生效 → 收费、关闭」，提前发现意外。

```bash

anvil --fork-url https://bsc-rpc.publicnode.com --no-storage-caching --port 8546 &
# 记下 pid，结束时只按这个 pid 结束，不要用 pkill -f
```
用 `cast` 完成（全部在 anvil 里，不上链）：
1. 部署新实现；impersonate 管理钱包，向时间锁 `scheduleBatch`（内容同 §5.2，延迟 172800）；用 `anvil_increaseTime` 快进 48 小时并出块；`executeBatch`。
2. 执行后读：`paused`、`whitelistNonce`、`params()`、`whitelisted(...)` 抽样、`depositNonce`、代理的 USDT 余额，与执行前逐项相同；`nativeFeeConfig()` = (收款地址, 50)。
3. `deposit` 带 `value=0.0005 BNB`（再试 0.0012 BNB），**无论 `txGasPrice` 是 0、0.05 gwei 还是 100 gwei**：收款地址都增加全额、发起人没有退款；`value=0.0004` 和 `0.0021` BNB、以及不带 `value`，都应回滚 `WrongNativeFee`。

### 5.1 提议方式

- **提议**：管理钱包在手机钱包 App 里，所以**不用 `cast` 签名**，而是用一次性页面 `tools/fee-batch-page`（在钱包内置浏览器里打开，只发两笔固定交易，页面检查连接的是管理钱包）。下面带 `--ledger` 的命令只是等价写法供核对，**不要照着在命令行签**；`scripts/schedule-fee-batch.sh` 只用于 `--dry` 演练。

**现成脚本（方案 A）：** `SIGN="<cast 签名参数>" bash scripts/schedule-fee-batch.sh bsc|wantos [--dry]`。它会先核对链上现场（旧实现、未暂停、纪元 0、无恢复流程、管理钱包、收款地址无合约代码），列出要提议的内容并解码，核对提案编号与预期一致，用管理钱包地址做一次无签名的模拟，然后要你输入 YES 才签名发送；`--dry` 只检查不发送。下面的手动命令是它的等价写法，供核对。
```bash

```
**核对（每条链）：**
```bash

```
把两条链的提案编号、交易哈希、最早可执行时间写进 §13「执行记录」。

**半途失败的处理：** 两笔提议是分开签名的。如果 BSC 那笔已经上链、WANTOS 那笔失败：**立刻取消 BSC 的提案**（`cast send $TL "cancel(bytes32)" <BSC 提案编号>`），再重新两条链都提议（换盐，例如 `-r2`）；或者马上重试 WANTOS 那笔，但把它的 `DELAY` 减去两笔之间的间隔，让两边到期时刻尽量接近。无论哪种，到期时刻两条链只能相差几分钟，期间只有一个方向收费是预期的。

### 5.4 排队期间
- 线上仍是旧合约，**所有功能不受影响**；白名单、转账、放款照常。
- 监控对时间锁提案和升级的反应：复审读代码得知，监控遇到不认识的事件会忽略，升级执行时会发 `UPGRADE_EXECUTED` 告警，这是预期，不代表出事；我没有在现场验证告警通道。
- **到点会自动执行**（见核心事实 2）：所以放行条件（§7）必须在 `DELAY` 到期之前满足；做不到就取消。**取消路径**：管理钱包或白名单钱包任一都可以 `cancel` 提案（管理页时间锁页面有取消按钮；或 `cast send $TL "cancel(bytes32)" $ID`）。取消后重新提议即可。
- **有效期**：到了最早可执行时间后 **14 天**内必须执行，过期作废。**建议留足余量：如果到最早可执行时间后第 10 天放行条件仍未满足，就取消并重新提议**，不要硬等。

### 入金（BSC → WANTOS）失败原因对照（降低失败率的清单，v0.3）

| 可能的失败原因 | 现在怎么防 | 剩余风险 |
|---|---|---|
| 附带的手续费和合约要求对不上（钱包改价、gas 价波动） | 合约不读 `tx.gasprice`，只夹 [MIN_FEE, MAX_FEE]；前端按报价附带，授权后重新报价 | 无（价格不再参与校验） |
| 附带金额超出区间（前端出错） | 报价函数的结果本来就在区间内；合约拒绝区间外的值，用户不会多付 | 前端出错会失败而不是多收 |
| 模拟调用被节点误拒 | 前端不设置 `gasPrice` 和 `gas`，交给钱包 | 无 |
| 旧合约没有报价函数 | 回滚按无手续费处理 | 网络错误会提示重试（不当成无手续费） |
| 退款发不回发起人（智能钱包） | 不再退款（仅费用被关闭瞬间才会原路退回） | 关闭瞬间正好有智能钱包带 `value` 的交易会失败，概率极小 |
| 报价和发送之间配置被改 | 每次发送前重新报价；改费率走 48 小时时间锁，有预告 | 极小 |
| 余额不够手续费 | 弹钱包之前就提示 | 属于正当拦截 |

**强制性说明：** 合约强制的是最低 `MIN_FEE`（0.0005 BNB）和最高 `MAX_FEE`（0.002 BNB）。诚实的前端按「gas 价高端 × 50」附带，gas 价上涨时多收；绕过我们前端直接调合约的人只付最低值。这是负责人接受的取舍。

**WANTOS 出金（`bridgeOut`）** 的手续费只由金额档位决定，与 gas 价无关，`value` 恰好等于报价。仍然可能的失败：档位在报价和发送之间被时间锁改动（有 48 小时预告，概率极小）。

**仍需真实验证：** 执行当天用 TP 钱包各做一笔，确认实际的手续费扣款与页面显示一致。

## 14.3 金库余额不足时的行为（负责人 2026-11-04 提出：补足后要自动恢复付款）

**结论：现有付款程序已经是这样设计的，不需要改代码；我加了回归测试证明。**
- 出金（WANTOS → BSC）和入金（BSC → WANTOS）在放款前都会检查对应金库的 USDT 余额；不够时订单进入 `WAITING`（原因 `reserve`），**立即发一次 `RESERVE_LOW` 告警**，之后不会反复刷告警。
- 付款程序每一轮都会重新评估 `WAITING` 订单；金库补足后**自动提交放款，不需要人工操作**。
- 大额订单已经排队（`QUEUED`），到期执行时金库被取空：订单不会变成 `FAILED`，继续等待，补足后自动付款。
- 回归测试：`packages/relayer/test/reserveResume.test.ts`（本地 anvil + 真合约）3 项：出金小额、出金大额排队、入金；全部通过。故意让付款程序不再评估 `WAITING` 订单，3 项都会变红。

**限制：** 一笔订单要付的金额加上已排队未放款的金额必须不超过金库余额才会被放行；补充金额不够覆盖时，订单继续等待。金库补充要由负责人转入，付款程序不会也不应该自动补钱。

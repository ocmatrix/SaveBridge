## 0. 红线（执行 PR-9 的任何人必须遵守）

1. 只在 **WANTON 1345** 与 **BSC 测试网** 上做；**绝不碰 WANTOS 主网 13555、BSC 主网、rpc1/rpc2、S1 验证者（101.32.41.231）**。
2. 测试资产转账由 **Testor** 代理，且必须有用户直接授权（目标地址 + 资产 + 金额）。任何「发交易」「部署」「加压」「改节点配置」都标记 `【需授权】`，授权是按动作的，不外推。
3. 私钥：管理钱包 / 白名单钱包的助记词只由负责人持有，开发方只拿地址；测试网用**单独的测试钥匙**，不得复用主网钥匙（含硬件钱包的主网账户）。
4. 不用 `pkill -f`；只停自己启动的进程 id。
5. 本计划中「演练」一律在测试网；WANTON 通过 ≠ 主网通过，主网上线前另有小额冒烟（PR10 手册）。

## 3. 部署与参数

### 3.1 部署顺序（每条链）

1. **A1/A2 授权后**：全新部署者 EOA（nonce = 0）；先模拟再广播，EIP-155 签名。
2. 按 `PredictAddresses` 预测 n / n+1 / n+2 三个地址（时间锁、实现、代理）；**两条链地址必须完全相同**；部署前核对两链部署者 nonce 为 0、预测地址无代码。
3. 部署：`BridgeTimelock(adminWallet, 预测的代理)` → 实现合约 → `ERC1967Proxy(impl, initData)`（部署与初始化同一笔交易）。
4. 部署后立即运行 `Verify.s.sol`：角色、时间锁成员与延迟（48h）、实现 codehash、参数、白名单为空、两链地址一致；结果存档到 `docs/` 之外的测试报告目录。
5. 部署者 EOA 不保留任何角色，演练「销毁私钥」流程。

### 3.2 失败规程演练（PR-0 ⑧）

- [ ] 故意让第 3 笔（代理）失败（例如初始化参数错误）→ 确认失败也耗掉 nonce → 按规程**两条链一起作废**，换新部署者 EOA 从头来；作废合约公告为非桥地址。
- [ ] 已部署一条链、另一条链失败 → 同样整体作废的演练。
- 通过判据：新一轮所有地址与上一轮不同，两链再次完全一致，验收脚本通过。

### 3.3 参数

按 DESIGN §5.5 初值部署，**测试网另备「压缩参数」组合**以缩短演练时间；压缩只能在测试网，且必须通过 `setParams` 的合法路径（时间锁 / 收紧）实现，不得改合约常量。

| 参数 | 初值 | 测试网压缩（演练用，待用户确认） |
|---|---|---|
| `dailyCap` / `perAddrDailyCap` / `largeThreshold` | 5,000 / 2,000 / 1,000 | 可收紧演练「撞额度」；放宽须 48h 时间锁，**时间锁延迟不可低于 48h（`MIN_DELAY` 为 immutable）** |
| `releaseDelay` | 12h | 范围下限 6h；收紧方向是增大，放宽（缩短）要走时间锁。若想缩短演练，部署时用初始值直接设为 6h（待确认） |
| `b2wDelay` | 15 分钟 | 下限 10 分钟 |
| 退款等待 24h、时间锁 48h、WL 交接 48h、WL 恢复 7 天、管理钱包恢复 14 天 | 常量 | **合约常量，不能缩短**。演练这些路径要么真等，要么用 anvil/fork 的 `vm.warp`（只能在本地 fork，不能在 WANTON 上）。见 §5.3 的分层策略 |
| `supplyCeiling` | 部署时 `totalSupply` + 1 万 | |

> **重要约束**：时间锁、退款等待、恢复窗口全是链上常量，无法在真实测试网加速。因此 PR-9 采取「**分层演练**」：真实测试网上等满真实时间的只做**每类一次**（建议并行开跑：先提议再做别的），其余用本地 fork（`anvil --fork` + 快进时间）做全量路径；两层的结论分别标注。

## 8. 跨链不变量「放款与退款最多一个」

> DESIGN §5.6 末尾：合约单链测试无法覆盖，放在本 PR 验证。涉及：同一 W2B 订单，BSC `Released`（放款）与 WANTON `executeRefund`（退款）**不得同时发生**。

### 8.1 机制回顾

- 合约 BSC 侧：`payouts[eventKey]` 终态 Released 或 Voided，互斥（不变量 2）。
- 退款先决条件：BSC `voidSource`/`cancelRelease` 且 finalized，然后 WANTON `requestRefund`（24h）→ `executeRefund`。
- 三道防线：①管理钱包发起、WL 24h 内可取消；②监控在可执行前 2 小时核对 BSC 上该 `eventKey` 为 Voided，不符则暂停 WANTON；③付款程序在每次 BSC 放款前重读 WANTON `orders[id].status == Locked`。

### 8.2 验证方法

| # | 对抗用例 | 预期 |
|---|---|---|
| X1 | 正常：BSC 作废 → `requestRefund` → `executeRefund` | 退款发生，BSC 该 key 无放款；监控核对通过 |
| X2 | **BSC 已 Released** 后管理钱包（模拟误操作 / 被盗）对该订单 `requestRefund` | 监控在可执行前 2h 发现 BSC 非 Voided → **暂停 WANTON**（一级）；WL 取消；`executeRefund` 在暂停时不可用；最终**只有放款** |
| X3 | 退款申请期间（Refunding），付款程序遇到该订单重试放款 | 付款程序重读 `status ≠ Locked` → 不放款（PR3 Gate2 A1/A2 回归：已批准的 REVIEW、已入队的 QUEUED、已签未广播的交易均不得发出；nonce 作废） |
| X4 | 竞态：同一区块窗口内 BSC 放款与 WANTON `requestRefund` | 终态之一；另一路被监控或付款程序拦下；记录最终账面 |
| X5 | `executeRefund` 到期瞬间 RPC 分歧 / BSC finalized 不可得 | 三条件缺一不暂停——**这是已知缺口**（PR7 风险 R2）；确认此时负责人收到 `CHECK_OVERDUE` 一级告警并人工取消 |
| X6 | B2W 方向对称：WANTON `queueRelease` 与 BSC `requestDepositRefund` | 对称拦截 |
| X7 | 付款钥匙被盗者抢先在 BSC 放款某未作废订单后再申请退款 | 同 X2 |

### 8.3 判据

**解除暂停**：负责人 `unpause` 后，旧事件只告警（`MISMATCH_ACKNOWLEDGED`），**只对解除之后的新事件再暂停**，不循环暂停。

# 管理页改造方案：管理钱包交接 + 参数页置灰

> 状态：**方案稿，待负责人确认后才开发**。范围只在 `apps/admin-web`（管理页 admin.wanto.pro）。**零合约改动、零链上写入。**
> 流程：本方案 → Figma 设计稿 → 负责人说「通过」→ 开发 → 自测 → 负责人说「发布」→ 发布。

## 1. 背景与目标

负责人提出两点：

1. 「交接与恢复」页看起来只有白名单钱包交接，需要把**跨链桥管理钱包交接**清楚地做出来，并讲清谁在哪一步签名。
2. 「参数」页里**当前做不了的操作要置灰**，避免运维误以为能改而产生矛盾。

核实结果（读代码，未在页面实操）：管理钱包交接的按钮在代码和线上包里**已经存在**（`HandoverPage.tsx`，每条链区块的第三个小标题），但埋得深、顶部又只有一个"白名单钱包/管理钱包"的证明角色下拉，所以被误认为没有。本次要解决的是**可发现性和流程表达**，不是缺功能。

## 2. 合约事实（已部署，不能改）

管理钱包交接（`BridgeTimelock`，DESIGN §4.6）：

| 步 | 谁签名 | 合约动作 | 说明 |
|---|---|---|---|
| ① 授权 | 现任管理钱包 | 经时间锁 `schedule` 一笔 `transferAdmin(新地址)` | 进入 48 小时等待 |
| ② 等待中撤销 | 现任管理钱包 **或** 白名单钱包 | 时间锁取消该提议 | 48 小时内随时可取消 |
| ③ 执行 | 任何人 | `execute` → `pendingAdmin = 新地址` | 候选有效期 7 天 |
| ④ 接收 | **新地址（TP 签名）** | `acceptAdmin()` | **上链即生效**；别人代签不了 |
| ⑤ 另一条链 | 两边各做一遍 | BSC、WANTOS 是两套合约 | 页面须标出只完成一条链 |

要点：
- 48 小时在**接收之前**，不在之后；接收后立即生效。
- 第③步之后到第④步之前（最长 7 天），合约里**没有**「旧管理员一键撤销待接收地址」的函数。
- 暂停期间不能提议更换；恢复进行中不能接收；新地址不能是已有钥匙持有人（KeyConflict）。
- 地址证明（新地址 `personal_sign` 一段文字）是**可选预检**，不上链，不授权。

## 3. 改造内容

### 3.1「交接与恢复」页重排

- 顶部**分段按钮**切换两个角色：「白名单钱包交接」「跨链桥管理钱包交接」。管理钱包交接默认可见，不再藏在每条链区块的第三个小标题下。
- 管理钱包交接按时间线排成 4 个节点，每个节点标明**谁签名**、**当前状态**：
  1. 现任管理钱包授权新地址（可选：先粘贴并验证新地址的地址证明）
  2. 等待 48 小时（显示倒计时；显示「撤销」按钮，管理钱包/白名单钱包可点）
  3. 执行提议（链接到「时间锁」页执行）
  4. **新地址在 TP 签名接收 → 生效**（节点上明确写「新地址签名后才生效」）
- BSC 与 WANTOS **并排两列**，各自显示 `待授权 / 等待中 / 待新地址接收 / 已生效`，任一链落后就在顶部显示"只完成一条链"提醒（沿用现有 `crossChainGaps`）。
- 已有的白名单交接、两种恢复保持原逻辑，只调整位置与分组，不改按钮行为。
- 在「待接收」状态下，页面直接说明：**此阶段合约没有一键撤销**，要收回请重新提议或联系白名单钱包发起恢复，避免运维误以为能撤。
- 新地址用 TP 打开 `/handover` 时，若该地址正好是某条链的待接收候选，页面顶部直接出现「接收管理钱包」主按钮。

### 3.2「参数」页置灰

- 判定沿用现有 `gate()`（链上读取，不新增权限逻辑）。当前钱包**不是该链管理钱包 / 未连接 / 暂停中（放宽）/ 恢复进行中**时：
  - 该链区块的**输入框一起置灰**（`disabled`），不只置灰提交按钮；
  - 旁边显示具体原因（如"当前钱包不是 BSC 的管理钱包（链上为 0x860f…5669）"）。
- **合约写死的项**（时间锁延迟 48h、各参数上下限）显示为只读文字并标注"合约固定"，不画成输入框；输入框旁显示该项允许范围（来自 `params.ts` 现有 `min/max`）。
- supplyCeiling 区块同样规则。

### 3.3 文案统一

页面与提示按合约真实顺序写：「授权 → 等 48 小时（可撤销）→ 新地址 TP 签名接收 → 立即生效」。删除任何暗示"新地址签名即生效/接收后再等 48 小时"的措辞。

## 4. 刻意不做的

| 不做 | 少了什么 | 缓解 | 何时再做 |
|---|---|---|---|
| **改合约，实现"新地址接收后再等 48h 生效 + 旧管理员可撤销"** | 与负责人设想的顺序不同 | 合约现有 48h 可撤销窗口等价保护；页面把顺序讲清楚 | 仅当安全评估认为"待接收空档"不可接受；需重新部署 + 迁移 + 重新审计，单独立项 |
| 新增"撤销待接收地址"的链上函数 | ③到④之间无一键撤销 | 页面明示 + 提议覆盖 / 白名单恢复两条现有路径 | 同上，随合约改造一起做 |
| 页面代办另一条链、一键双链提交 | 运维要在两条链各点一次 | 并排两列 + 缺口提醒 | 出现漏做一条链的实际事故后 |
| 新增后端、通知、持久化 | 无自动提醒接收 | 状态全部实时读链；倒计时在页面 | 运维反馈需要提醒时 |
| 改动 Cloudflare Access / 部署结构 | — | 保持现状（`/handover` 公开，新地址要能在 TP 里打开） | 无 |

## 5. 安全与回退

- 零合约改动；页面只读链上状态，交易仍由用户钱包签名，页面不持有任何密钥。
- 置灰只是**防误操作的体验层**，权限最终由合约裁决；即使前端判错，链上也会拒绝（fail-closed）。
- 发布前先记录当前线上版本 ID 作为回退点；发布到 Cloudflare Worker `savebridge-admin`（不碰 `savebridge-bridge`）。
- 发布只在负责人明确说「发布」之后进行；本方案不含生产写入。

## 6. 验收（要能证明会红）

沿用 admin-web 现有 vitest（当前 94 项通过），新增/调整用例，每条都要"改坏实现后变红"：

1. 管理钱包交接四个节点的状态机：给定链上快照 → 断言各节点状态与可点按钮（含"待接收时无撤销按钮并有说明"）。
2. 两条链状态不一致时显示"只完成一条链"。
3. 非管理钱包 / 未连接 / 暂停 / 恢复中：参数页**输入框 disabled** 且有原因文案。
4. 合约固定项渲染为只读，不含 `<input>`。
5. 新地址为待接收候选时，页面顶部出现「接收管理钱包」按钮；非候选地址不出现。
6. 文案回归：页面不出现"接收后再等 48 小时"之类措辞。

验收手段：本地构建 + 内置浏览器走查两页（桌面与手机宽度）；不接生产钱包，不发任何交易。

## 0. 业务规则（已由负责人确定）

| 方向 | 规则 |
|---|---|
| 入金 BSC → WANTOS | **不设限**：无白名单、无排队、无最小金额，即时放款。只受全局暂停开关约束。放款后由监控核对（见 §4a） |
| 出金 WANTOS → BSC | **设限**：WANTOS 侧 `bridgeOut` 需发起人在白名单内，有每地址日额、供应上限；BSC 侧放款收款地址需在白名单内，大额（超过 `LARGE_THRESHOLD`）延迟 `RELEASE_DELAY` |
| 白名单 | 白名单钱包**只签一次**，两条链同时生效。后台用 WANTOS 登录授权，**不切换网络** |
| 暂停 | 全局暂停开关保留，作为最后兜底，只由负责人手动执行 |

## 4a. 监控（D10，方案 A，已定）

**目标**：简单、能看见问题、能告警。不做放款前拦截，不做新功能。

| 项目 | 规则 |
|---|---|
| BSC 节点 | 2 个独立 RPC，不同服务商、不同机器（设计最低线）。不再追求 3 个 |
| WANTOS 节点 | 沿用现有 WANTOS 监控，只看 WANTOS 侧的出金与放款结果 |
| 入金（BSC → WANTOS） | 不排队、不做放款前核对。放款后比对 BSC 存款与 WANTOS 放款：**①** 编号、收款人、金额三项必须一致，不一致则告警；**②** 从 BSC 存款首次上链（latest，D11）到 WANTOS 放款完成，超过 **5 分钟** 则告警。若该存款之后因重组被推翻，会表现为一致性告警，由负责人人工核对 |
| 出金（WANTOS → BSC） | 核对白名单与额度，异常则告警 |
| 暂停 | 只由负责人手动执行。监控不自动暂停 |
| 心跳 | 外部心跳服务，监控、付款程序各一个检查项 |

**明确不做**：BSC 放款前拦截、自动暂停、按订单冻结、三节点共识。

**风险接受**：入金放款前不再有链上核对，异常只能事后发现。负责人已接受此风险（D10）。

## 5. 部署步骤

### 5.1 准备（不上链）

1. 完成 §3 全部代码改动（C1–C6），`forge test` 与各包测试全部通过；记录改动前后的 codehash。
2. 冻结参数文件，计算并存档 sha256（§4）。
3. 预测地址（纯计算）：`contracts/script/PredictAddresses.s.sol`，环境变量 `DEPLOYER`、`DEPLOYER_NONCE=0`。得到三个地址：时间锁（nonce 0）、实现（nonce 1）、代理（nonce 2，即桥地址，两链相同）。
4. 负责人在独立渠道复算一次预测地址，与上面一致才继续。

### 5.2 部署者注资【G1】

- 模拟估算 gas（BSC 三笔、WANTOS 三笔，加余量）。
- 负责人授权后，向部署者转入仅够部署的 BNB 与 WANT。
- 核对：两链上部署者 nonce 均为 0，余额到账。

### 5.3 部署【G2 BSC，G3 WANTOS】

**每一笔：先模拟，再广播。一笔一核对。**

1. 先 BSC，后 WANTOS。BSC 三笔全部核对无误，才开始 WANTOS。
2. 模拟：不带广播参数运行 `contracts/script/Deploy.s.sol`，核对输出地址与预测一致，核对环境变量（`SIDE`、`PEER_CHAIN_ID`、`TOKEN`、角色地址、参数）。
3. 广播：仅在模拟完全一致、且负责人已授权后。
4. 记录每笔交易哈希、区块号。**代理的部署区块 = 监控 `startBlock`**，单独记录。
5. 验收：`contracts/script/Verify.s.sol`，环境变量按脚本要求逐项填写。验收不通过，停止，不进入下一步。

**失败规程**：任何一笔失败都会消耗 nonce。此时两条链一起作废，换新的部署者 EOA 从头来，不得在已消耗 nonce 的部署者上补发。

### 5.4 部署后收尾

1. 在 BscScan 与 scan.wantos.io 上开源验证三个合约（solc 0.8.28、cancun、optimizer runs = 1、via_ir = false）。
2. 确认部署者不持有任何角色（验收脚本会断言）。
3. 销毁部署者私钥（恢复的旧钥匙、新钥匙都要销毁），记录销毁方式。
4. 存档部署清单：地址、交易哈希、区块号、参数哈希。

## 6. 应用切换（顺序固定）

1. **监控（rpc3）**：更新桥地址、两链 `startBlock`、时间锁地址。先启动监控，并确认两条告警（不一致、超过 5 分钟）能正常发出，再继续。
2. **付款程序（ss02）**：更新桥地址；旧订单记录归档，避免被当作新订单处理。
3. **前端（bridge-web）**：更新 `VITE_BSC_BRIDGE`、`VITE_WANTOS_BRIDGE`，重新构建并跑 `check-dist --real`，再发布。
4. **白名单【G4】**：白名单钱包签名一次，两条链同时提交。首批名单重新提交，旧合约的白名单不会自动带到新合约。T0 和测试地址都要在名单里。
5. **注资【G5】**：新合约用新的 USDT 注资，金额由负责人决定。

## 7. 测试顺序（冒烟，每笔至少 10 USDT）

1. 入金一笔（BSC → WANTOS）：确认即时到账，不排队；监控比对一致，无告警。
2. 出金一笔（WANTOS → BSC）：确认白名单检查通过，BSC 侧放款成功，监控无告警。
3. 再各跑一笔，确认没有重复放款。
4. 故意用未入白名单的地址出金一次，确认被拒绝（这一步需要负责人确认是否要做）。
5. 告警演练：人为制造一次不一致（或超时），确认告警到达负责人（这一步需要负责人确认是否要做）。

## 8. 旧合约退役（新合约部署完成之后再提议，D8）

1. **先提取，不要先暂停**。`withdraw` 需要合约未暂停（`whenNotPaused`），先暂停会导致提取失败。
2. 管理钱包提议时间锁 `withdraw`（BSC 约 14 USDT，WANTOS 约 12 USDT，提取前重新核对余额），48 小时后执行。
3. 撤销旧合约上 relayer、pauser 的角色。
4. 最后暂停旧合约，并公告为非桥地址。
5. 核对旧合约上没有遗留的 QUEUED 记录。

## 9. 停止条件

- §1 中出现新的「待定」项且未确认。
- C1–C5 任一测试未通过，或审计未完成（且负责人未书面接受风险）。
- 模拟输出与预测地址不一致。
- 任一笔部署失败（触发两链作废）。
- Verify 不通过。
- 监控告警不能正常发出。
- BSC 放款钥匙 BNB 低于告警线。

## 10. 刻意不做的

- 不做按订单冻结（D5），不加入新的入金限制。
- 不做放款前的 BSC 存款核对（D10）。

- 不复用旧合约地址，不升级旧合约。
- 不在没有负责人授权的情况下广播任何交易。
- 不把任何私钥、口令写入本文件或聊天。

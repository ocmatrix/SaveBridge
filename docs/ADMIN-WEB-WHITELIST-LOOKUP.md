# 管理页新增：白名单查询 + 添加前"先核对"并自动排除已在名单的地址

> 状态：**方案稿，待负责人确认后才开发**。范围只在 `apps/admin-web`。**零合约改动、零链上写入。**
> 流程：本方案 → Figma 设计稿 → 负责人说「通过」→ 开发 → 自测 → 提交合并 → 负责人说「发布」→ 发布。

## 1. 背景与目标

1. 能快速查到**某个地址是否在白名单里**（BSC、WANTOS 各自的状态）。
2. 添加白名单时，提交前先**核对**名单里每个地址现在是否已经在白名单；**已经在的自动排除**，不再重复提交，省 gas。

## 2. 现状（读最新 `main` 代码得到）

- 合约 `applyWhitelistBatch` 对批里**每个地址都无条件写一遍** `whitelisted[a] = allowed` 并发一条 `WhitelistUpdated` 事件，不管它原来是不是已经在名单里。已在名单的地址再提交，纯属白花 gas、白多一条事件。
- 白名单页"2. 逐行参考信息"已经有一列"是 / 否"（BSC / WANTOS），但：只读**当前这一页（≤500 行）**，只作提示，**不过滤**，也不要求先看。
- `runJob` 只在"整批在某条链上**全部**已是目标状态"时才跳过这条链；批里只要混了一个新地址，整批照常提交。
- 没有按地址查询的页面。"当前白名单"区块靠扫链上日志还原整份名单，慢，也不适合查一个地址。
- 现有"页面上取消地址"的机制：`unchecked` 集合 + 提示"离线核对前请先在原始文件里删掉它们（或核对导出的清单）"。本方案的自动排除沿用这一机制，不另造并行机制。

## 3. 方案

### 3.1 新页面 `/lookup`「白名单查询」

- 输入：文本框，一次可粘贴一个或多个地址（每行一个；沿用现有地址解析规则 v1：格式、EIP-55 校验、去重），**最多 500 个**。
- 点「查询」：对每个地址读两条链的 `whitelisted(address)`，显示表格：地址 | BSC 是/否 | WANTOS 是/否。
- 顶部汇总：两条链都在 N 个、只在一条链 M 个、都不在 K 个。格式错误的行单独列出原因，不参与查询。
- 只读，不需要连接钱包。

### 3.2 白名单页：添加前「先核对」

在"1. 上传或粘贴地址"之后、"3. 核对并签名"之前，增加一步：

1. **「先核对」按钮**：读**整份名单**（不只当前页）在两条链上的当前状态。50 个一批做 JSON-RPC 批量读，两条链并行，显示进度，可取消。
2. **排除规则**（沿用"两条链用同一份名单、一次签名两边通用"的设计，不能每条链各发各的名单）：
   - **添加**：两条链**都已在**白名单的地址 → 自动排除；只在一条链已在的 → **保留**（另一条链还需要写入）。
   - **移除**：两条链**都已不在**白名单的地址 → 自动排除；其余保留。
3. 核对结果区显示：`已在白名单（已排除 N 个）`（可展开看清单）、`只在一条链已在名单（保留 M 个）`、`将提交 K 个`。全部被排除时提示"无需提交"。
4. **未核对不能往下走**：「准备本批」在"当前名单 + 当前模式"完成核对前置灰并写明原因（"请先核对"）；名单或添加/移除模式一变，核对结果作废、需重新核对。
5. **读取失败不放行**（默认拒绝）：任一链读取失败则显示原因和「重试」，不允许跳过核对。
6. **与离线核对的关系**：自动排除后的名单会和原始文件不同。沿用现有提示，把自动排除的地址也计入"页面上已排除"，提示负责人用**导出的清单**做离线核对（listHash 对不上是正常的）。
7. 签名前 `runJob` 仍会再读一次链上状态（已有逻辑，不改），防止核对之后链上又变了。

### 3.3 不改的东西

合约、提交 Function、签名与哈希规则（名单规则 v1）、离线核对工具、批次大小 500、写入顺序。

## 4. 刻意不做的

| 不做 | 少了什么 | 怎么缓解 | 何时再做 |
|---|---|---|---|
| 用 Multicall / 新增合约批量读接口 | 5000 个地址要约 100 批/链，核对要几十秒 | 50 个一批 JSON-RPC 批量、两条链并行、显示进度、可取消；rpc3 限流是"单请求并发 429、批量放行"，与现有读取方式一致 | 名单常超 5000，或节点限流频繁 |
| 两条链各发各的名单（只在一条链已在的也排除） | 个别地址会在已在名单的那条链上多写一次 | 一次签名两边通用的价值更大；多写一次只多几千 gas | 若这类地址占比很大 |
| 查询页做全量名单浏览 / 导出 / 搜索 | 看不到完整名单 | 已有"当前白名单"区块 | 有人需要时 |
| 缓存或保存核对结果 | 每次都要重新读 | 链上状态会变，签名前本来就会再读；保存反而可能过期 | 无 |
| 后端或管理接口参与 | 无 | 全部直接读链，不依赖 `VITE_ADMIN_API` | 无 |
| 核对失败时允许"跳过" | 节点故障时不能提交 | 可重试；紧急情况走链上现有路径 | 无 |

## 5. 安全与回退

- 只读链上，不新增任何写入；排除只会**减少**提交的地址，不会增加。
- 过滤逻辑是一个纯函数，输入"名单 + 两条链状态 + 模式"，输出"保留 / 排除"，便于测试。
- 回退：Cloudflare Pages 控制台回滚到上一个部署（发布前记录当前部署 ID 作为回退点）。发布仍需负责人明确说「发布」。

## 6. 验收（要能证明会红）

沿用 admin-web 现有 vitest + 本地双链：

1. 纯函数：添加 / 移除 × 两条链各种组合（都在、只在 BSC、只在 WANTOS、都不在）→ 保留与排除正确；改坏规则（把"都在"改成"任一在"）用例必须变红。
2. 页面：未核对时「准备本批」置灰且有原因；核对后先前已加白的地址被排除、计数正确；全部已在名单 → "无需提交"；名单或模式变化后核对作废；任一链读取失败 → 不放行并可重试。
3. 查询页：已在 / 不在 / 只在一条链 / 格式错误 / 超过 500 个。
4. 回归：现有白名单页和 `/lookup` 以外的页面测试不变。
5. 本地构建后用内置浏览器走查手机和电脑宽度；不接生产钱包，不发任何交易。

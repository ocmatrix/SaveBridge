## 0. 总规则（先读）

1. **生产写入必须有用户在对话里明确说出的授权**：部署、注资、切换、写白名单、启用服务、发布前端、任何向主网广播的交易。授权是按步骤的，不外推；每步前在下表 §2 的授权闸门里取得。
2. **合并**（PR / 分支）必须用户亲口说「合并 #N」。本手册不包含合并。
3. 灰度发布的内容、已签名的不可变内容（发布产物哈希、部署参数、initcode 哈希）**不得原地修改**：要改就重新走冻结和验收。
4. 任何 WANTOS 链维护（升级、rollback、换二进制）之前**先暂停桥**（DESIGN §6.2）。
5. 不碰 rpc1 / rpc2 / S1 验证者的运维配置（沿用 `memory` 红线）；与本桥相关的链运维需要用户另行授权。
6. 部署者 EOA 的私钥只在干净离线设备上生成并使用，部署完成后销毁；开发方永远不接触管理钱包和白名单钱包的助记词，只拿地址（PR0 ③）。
7. 每一步都留下记录：交易哈希、区块号、时间、操作者、截图；存档目录由用户指定（见 §14）。
8. 任何一步的检查未通过：**停下**，不重试、不绕过，回到 §12 判断是否触发停止条件。

## 3. 部署（全新部署者 EOA）

### 3.1 准备

- [ ] 在**干净离线设备**上生成部署者 EOA 私钥（不经过任何旧工具）；记录地址 `DEPLOYER`；**仅在该设备签名**，用离线签名方式把已签交易带到联网机器广播
- [ ] 已确认的部署输入（全部来自负责人，开发方只复核）：
  - 管理钱包地址 `ADMIN_WALLET`（时间锁提议人）
  - 白名单钱包地址 `WL_WALLET`（必须是 EOA）
  - 付款钥匙地址：BSC 一个、WANTOS 一个（来自 KMS，**两条链不同**）
  - 暂停钥匙地址：BSC 一个、WANTOS 一个
  - 两条链的四类钥匙**两两不同**（桥合约 `initialize` 会检查）；`ADMIN_WALLET != WL_WALLET`
  - WANTOS-USDT `0xc74F2e7fBdA2af9D1fc26b85E341229063Dc0873` 与 BSC-USDT `0x55d398326f99059fF775485246999027B3197955`
  - 对端链 ID：WANTOS 13555、BSC 56（各自 `peerChainId`）
  - 参数 `Params`（DESIGN §5.5 初值，**待用户最终确认**，见 §14）；WANTOS 的 `supplyCeiling`（部署时 `totalSupply` + 1 万，**部署前一刻重新读取 `totalSupply`**）
- [ ] 部署参数文件冻结，计算其哈希并存档（"不可变内容不得原地修改"）

### 3.2 部署者注资【G1】

- [ ] 估算 gas（模拟）：BSC 三笔、WANTOS 三笔，加余量

- [ ] 核对两条链上 `DEPLOYER` 的 **nonce 均为 0**；两条链**用同一个 EOA**

| nonce | 合约 | 预测地址（填入） |
|---|---|---|

| 1 | 桥实现合约（构造函数 `_disableInitializers()`） | `____` |

- [ ] 两条链上这三个地址**均无代码**
- [ ] 负责人在**独立渠道**（不同设备、不同工具）复算一次预测地址，与开发方一致
- [ ] 把预测地址写进公告草稿和前端配置草稿（不发布）

### 3.4 部署【G2 BSC / G3 WANTOS】

每一笔：**先模拟，再广播**；EIP-155 签名；一笔一核对。

1. [ ] `new BridgeTimelock(ADMIN_WALLET, predictedProxy)` → 地址 = 预测的 nonce 0
2. [ ] `new BscVaultV2()` / `new WantosBridgeV2()`（实现）→ 地址 = 预测的 nonce 1
3. [ ] `new ERC1967Proxy(impl, abi.encodeCall(initialize, InitArgs))` → 地址 = 预测的 nonce 2；`InitArgs.timelock` = nonce 0 地址，`peerBridge` = nonce 2 地址（= 自身）
4. [ ] 记录三笔的交易哈希、区块号（**代理的部署区块 = 监控 `startBlock`**）
5. 建议顺序：先 BSC 全部三笔，核对无误，再 WANTOS 三笔（任何一边失败，两边一起作废）

**失败规程**：任何一笔失败（失败也耗掉 nonce）→ **两条链一起作废**，换新的部署者 EOA 从头来；作废的合约公告为非桥地址；已转入的 gas 回收后重新走 §3.2。不得在已消耗 nonce 的 `DEPLOYER` 上"补发"以凑齐地址。（PR9 §3.2 已演练。）

## 5. 钥匙仪式（部署前后分工）

> 钥匙地址在部署前就要确定（构造/初始化参数）；仪式分「部署前」与「部署后确认」两段。

### 5.1 部署前

- [ ] 管理钱包：负责人本人在硬件钱包上生成，离线抄写助记词到金属板，**分两处保管**，不拍照不上传
- [ ] 白名单钱包：**另一个**硬件钱包，**分设备、分地点**，同上
- [ ] 部署者 EOA：干净离线设备（§3.1）
- [ ] 付款钥匙：KMS 内部生成，私钥不出 KMS；记录地址、KMS 密钥标识、访问策略（只允许服务器 A）
- [ ] 暂停钥匙：服务器 B 本机或 KMS，只能暂停
- [ ] 提交服务热钥匙：服务器 A 本机，gas 只放 3 天用量
- [ ] 每把钥匙生成后立即做「小额测试签名」确认设备和备份可用（管理 / 白名单钱包做一条无资金消息签名）
- [ ] 把 4 类地址交给开发方；开发方**只收地址**

### 5.2 部署后（上线前最后确认）

- [ ] 管理钱包在主网做一次**不改状态**的链上动作的模拟（例如 `eth_call` 形式的 `freezeWhitelist` 模拟，不广播），确认设备能签；**不要真的冻结**
- [ ] 白名单钱包对一条主网 EIP-712 域下的测试消息签名（不提交），确认设备显示与离线工具的 domain / message hash 一致（与 PR9 R2 对比）
- [ ] 两个钱包的 gas 余额在两链足够，并加入 `gasWatch`
- [ ] 钥匙备份异地恢复演练（每季度一次的首轮；PR0 ③ 第 4 条）

## 6. 服务上线顺序【G4】

> 服务只读主网地址、不持有管理权；顺序：先监控，再付款程序，最后前端。

1. [ ] **服务器 B（监控）**：写配置（两链 `chainId / rpcUrls(≥3) / bridge / timelock / token / startBlock`；`gasWatch` 含两个钱包与暂停钥匙；`legacyAddresses`：`0x8dFd`（WANTOS）、`0x9dab`（两链）、`0xec6e`（BSC））→ 启动 → 启动自检（RPC chainId、decimals）→ 确认**零一级告警**
2. [ ] 监控心跳：停止 → 外部服务在超时后电话 / 短信负责人（一次真实演练，再启动）
3. [ ] 一级告警真实触发演练：例如在主网只读状态下由监控发出测试告警 `TEST`（不暂停），确认电话 + 短信到达，并通过 ack 入口确认
4. [ ] **服务器 A（付款程序）**：配置（RPC 来自环境变量，配置文件不含 URL；KMS 地址固定；启动自检 `eventKeyOf(1)` 等于自算 key、`peerChainId/peerBridge` 一致、三把发送钥匙两两不同）。**此时白名单为空，不会处理任何订单**

### 回滚

> 链上合约不可"撤回"；回滚 = **收紧到关闭 + 保护资金**。所有"防守动作"负责人可随时自行执行，无需等待授权。

| 级别 | 动作 | 谁 / 多快 |
|---|---|---|
| R0 观察 | 仅告警，不停 | — |
| R1 暂停受影响的链 | `pause()`（监控自动，或负责人任一钱包手动）；暂停期间升级、换钥匙、取消、作废、移除仍可用 | 立即 |
| R2 停止新放行 | 冻结白名单写入 `freezeWhitelist()`；`emergencyRemove` 移除可疑地址（**先冻结再移除**，PR1-NOTES §5.11a-1） | 管理钱包立即 |
| R3 摘钥匙 | `revokeKey(RELAYER_ROLE/PAUSER_ROLE, 地址)`；取消排队项 `cancelRelease`；`voidSource` / 批量；`cancelRefund` | 管理钱包 / 白名单钱包立即 |
| R4 退单 | 对已 Locked 但不会被放款的订单：BSC 作废（finalized）→ `requestRefund(Batch)` → 24h → 任何人 `executeRefund`；B2W：WANTOS 作废 → `requestDepositRefund` → 24h → 执行 | 24h 起 |
| R5 收缩流量 | 白名单移除（先 WANTOS 后 BSC）使在途订单进入退款；收紧额度（立即） | 管理钱包 |
| R6 取回储备 | `withdraw(to, amount)` 经时间锁 48h（暂停期间不可执行，需先解除暂停） | 48h |
| R7 换桥 | 无链上最后手段（决定 15）；靠链下沟通、部署新桥另行安排 | 链下 |

要点：
- 暂停期间 `withdraw` 与放宽参数**不能**执行；回滚到 R6 需先 `unpause`（负责人任一钱包）。
- 提议期（48h）内白名单钱包可取消管理钱包的任何恶意提议；**负责人必须在 7 天内响应恢复告警**。
- 回滚后的状态应写入事故报告，并回到 §1 门槛重新评估。

## 12. 停止条件与处置

### 12.1 立即停止（并暂停受影响的链，负责人可立即自行执行）

出现任一项：
- 监控自动暂停（`AUTO_PAUSE`）或 `PAUSE_FAILED`
- 对账短缺（`RECONCILE_SHORTFALL`）无法在当天解释
- 任何**未经负责人本人发起**的时间锁提议、角色变化、交接 / 恢复启动
- WANTOS 区块 hash 变化（回滚）、WANTOS 出块停滞、BSC 取不到 finalized 持续
- 付款钥匙 / 管理钱包 / 白名单钱包 / 暂停钥匙疑似泄露
- 旧金库 `0x8dFd`、旧付款程序 `0x9dab` 异常动作且无法解释
- 增发超过阈值导致 `bridgeOut` 被 `supplyCeiling` 拒绝（先判断是否为业务停摆，按 §11 应急手册处置）
- 监控或付款程序失联超过心跳阈值
- 放款或退款出现同一订单"放款与退款同时"迹象

### 12.2 暂停放大（不暂停桥，但停止灰度推进）

- 二级告警连续出现且原因不明（节点落后、RPC 分歧、`CHECK_DEFERRED` 长时间）
- 订单延迟 > 阈值的比例异常
- 储备不足 1 天
- 日报与链上白名单变更不一致

### 12.3 处置顺序（DESIGN §9.1 / §11）

1. 看一级告警详情（`reason / observed / check`）。
2. 确认可疑 → **先吊销被怀疑的付款钥匙** → **取消可疑排队项** → **再解除暂停**。
3. 确认误报 → 直接解除暂停，检查 RPC 配置。
4. 经时间锁补发新的付款钥匙（48h）。
5. 事件复盘；重置 §11.2 的 72h 计时。

### 12.4 场景速查（DESIGN §11，生产版）

| 场景 | 第一反应（负责人） |
|---|---|
| BSC 付款钥匙泄露 | 暂停 BSC → `revokeKey` → 取消排队 → 解除暂停 → 48h 补发新钥匙；损失上限约 `dailyCap` |
| WANTOS 付款钥匙泄露 | 暂停 WANTOS → 吊销 → 取消可疑项 → 解除暂停 |
| 暂停钥匙泄露 | 任一钱包解除暂停；吊销；经时间锁补发 |
| 管理钱包丢失 | 白名单钱包 `startAdminRecovery`（14 天）；期间白名单禁写 |
| 白名单钱包丢失 | 管理钱包 `startWhitelistRecovery`（7 天）；期间白名单禁写 |
| 管理钱包被盗 | WL 逐条取消恶意提议与恢复；7 天内响应恢复告警 |
| 白名单钱包被盗 | 管理钱包**先冻结**白名单 → 移除可疑地址 → 否决交接 → 启动 WL 恢复 |
| 两个钱包同时被盗 | 无法阻止；损失上限是整个储备 |
| 管理后台被篡改 | 不签；离线核对 `listHash` / message hash |
| 增发 | 只告警；必要时经时间锁提高 `supplyCeiling`（48h） |
| 云账户 / KMS 丢失 | 经时间锁补发付款钥匙（48h）；桥只停不丢钱 |

三条注意（DESIGN §11 补充）：①紧急移除前先冻结；②被盗 WL 能作废未来 orderId（走 WANTOS 退款，人工处理）；③重复 `pause()` 回滚 `EnforcedPause`，监控视为成功。
